# Offline authenticity-signal prep: toy mechanisms (synthetic, non-intimate)

> **This repository has two separate parts.**
>
> 1. **Toy preparation**: `authexp/`, `run_experiment.py` and [`RESULTS.md`](RESULTS.md). These use a toy signed manifest (not C2PA) and a toy watermark (not SynthID or any production scheme). They are preparation only, and their results do not settle questions about actual signals.
> 2. **Actual C2PA evaluation**: `actual_c2pa/` and [`RESULTS_ACTUAL_C2PA.md`](RESULTS_ACTUAL_C2PA.md). These run the official `c2patool` offline on official C2PA test files, and on synthetic images signed with c2patool's bundled TEST credentials. See "Actual C2PA evaluation" below.
>
> **Still unevaluated:** production watermarks, SynthID and AI-image detectors. [`docs/ACTUAL_SIGNAL_ROUTES.md`](docs/ACTUAL_SIGNAL_ROUTES.md) lists the smallest real route for each, with the decision it needs, its source, setup and cost, and what stays unevaluated if it is skipped.

A small, bounded, offline preparation exercise. Using toy mechanisms, it shows what three kinds of signal can and cannot establish about an image:
- provenance (a signed manifest);
- watermarks;
- plain metadata.

It also shows where each one fails, and where the honest answer is to abstain.

It accompanies the research report in [`docs/`](docs/). The report reviews public evidence on telling whether social-media photos and videos are AI-generated. This repository adds a reproducible, hands-on illustration of the report's main distinctions. It does not attempt to estimate real-world performance.

## Scope and safety

- **Synthetic, non-intimate images only.** The images are deterministic procedural landscapes and geometric shapes, 256×256, generated by this code. There are no people, no real photographs, no intimate content and no private cases.
- **No verdicts.** Nothing here certifies any image as real or fake. The output is a set of statements about what each signal supports, with explicit abstentions.
- **Toy schemes, clearly labelled:**
  - The provenance manifest (`authexp/manifest.py`) is a toy format. It is **not C2PA** and implies nothing about C2PA conformance.
  - The watermark (`authexp/watermark.py`) is a toy keyed spread-spectrum scheme. It is **not SynthID** or any production watermark, and its robustness numbers do not describe production systems.
- **Unevaluated:**
  - **AI-image detectors.** None was available offline, so no detector scores were produced or estimated.
  - **C2PA verification.** No C2PA tool was installed.
- **Test keys are not secret.** The Ed25519 keys are derived from public labels so the run is reproducible. Do not reuse them.
- **Not legal advice and not a product.** There is no real-user pilot, outreach or automatic reporting.

## Requirements

Everything runs offline, using the Python standard library and locally installed command-line tools:
- Python 3.10 or later;
- `openssl` with Ed25519 support (tested with OpenSSL 4.0.3);
- libjpeg-turbo `cjpeg`/`djpeg`, for JPEG re-encoding;
- libwebp `cwebp`/`dwebp`, for WebP re-encoding;
- optionally, macOS `sips`, to test what an operating-system converter keeps.

No packages are installed and no network access is needed.

## Run

```sh
python3 -m unittest discover -s tests -v   # 33 tests (actual-C2PA integration tests skip if c2patool is absent)
python3 run_experiment.py                  # full run (about 1 minute); writes results/results.json and RESULTS.md
python3 run_experiment.py --quick          # fast smoke run; writes results/results_quick.json
python3 make_manifest.py                   # writes MANIFEST.md (environment, parameters, hashes)
```

## What was tested

1. **Provenance.** A toy signed manifest: Ed25519 signature over the claims plus a SHA-256 binding to the decoded pixels, checked against a toy trust list with optional revocation. There are 16 cases:
   - an intact file;
   - the manifest stripped;
   - re-encoding, a crop or a single-value pixel change, each with the manifest copied across;
   - unsigned metadata edited;
   - the manifest moved onto a different image;
   - a self-signed forgery;
   - a spoofed key ID;
   - a trusted key signing a false "capture" claim;
   - a revoked key, checked with and without revocation;
   - signed claims edited after signing;
   - two real conversions through macOS `sips`.
2. **Watermark.** A toy keyed watermark at amplitude ±3, detected by correlating a high-pass residual against the key's pattern with threshold z ≥ 4. Measurements:
   - detection after JPEG (q90 to q15), WebP (q80 to q20), downscaling and upscaling, small crops, and a `sips` JPEG round-trip;
   - the false-positive rate on unmarked images scored with unrelated keys;
   - a copy attack that spoofs the mark onto images from a different generator.
3. **Plain metadata.** Camera-style text claims written onto a synthetic image, and whether they survive conversions.
4. **Evidence-to-statement mapping** (`authexp/evidence.py`). Each signal state maps to the strongest statement it supports, or to an abstention. Never to "real" or "fake".

## Results of the recorded toy run (preparation only)

These numbers describe the toy mechanisms only. They are not results for C2PA, SynthID, any production watermark or any AI-image detector.

Full numbers are in [`RESULTS.md`](RESULTS.md) and [`results/results.json`](results/results.json). The environment and hashes are in [`MANIFEST.md`](MANIFEST.md).

| Signal | Observation (this run) | What it does and does not establish |
|---|---|---|
| Signed manifest, intact, trusted key | `VALID_TRUSTED` | That the trust-listed key holder signed these claims, and the pixels are unchanged since signing. Not that the scene or the claims are true. |
| Trusted key signs a synthetic image as a "capture" | `VALID_TRUSTED`, with a false claim | A trusted signature attests who signed, not what is true. This mirrors a trusted signing pipeline being fed non-camera content. |
| Self-signed forgery | `VALID_UNTRUSTED` | The signature is cryptographically fine, but the signer's identity is unknown. Valid is not the same as trusted. |
| Revoked key | `VALID_REVOKED` when revocation is checked; `VALID_TRUSTED` when it is not | The outcome depends on the validator's policy, not only on the file. |
| JPEG q90, WebP q80, 8 px crop or a 1-value pixel change, manifest kept | `BINDING_MISMATCH` in every case | A benign re-encode and a deliberate edit are indistinguishable to a hard pixel binding, so the right answer is to abstain. |
| Manifest stripped; macOS `sips` re-save; `sips` JPEG round-trip | `NO_MANIFEST` in every case | The OS converter dropped the manifest chunk and the text metadata. Absence is not evidence either way. |
| Unsigned text metadata edited | Manifest still `VALID_TRUSTED` | Metadata outside the signed manifest is unprotected. |
| Watermark: marked versus unmarked | 12/12 detected (median z 135); 0/24 unmarked detected | Supports that this key's pattern is present. Absence on another generator's images says nothing about authenticity. |
| Watermark false positives | 0/960 null trials at z ≥ 4 (null z mean −0.03, sd 1.00, max 3.18) | 95% upper bound on the false-positive rate is about 0.31% (rule of three). The theoretical rate is about 3×10⁻⁵ if the null is exactly normal. |
| Watermark after JPEG q90 / q75 / q50 / q30 / q15 | 12/12 at each quality; median z 69 / 31 / 13 / 8.3 / 5.5 | The score falls steadily with compression. This toy mark at this size survived all tested JPEG qualities. |
| Watermark after WebP q80 / q50 / q20 | 12/12, 11/12, 4/12 | Strong recompression removes it in many cases. |
| Watermark after halving then doubling | 12/12 (median z 27) | Survived this resize. |
| Watermark after a 1 px or 8 px crop | 0/12 and 0/12 | The fixed-origin detector loses alignment. The 1 px crop gives strongly negative scores (median z −17.6), a sign of misalignment rather than absence. |
| Copy attack, without the key | 12/12 spoofed images detected (median z 134) | A detected watermark can be forged onto other content, so detection supports a claim that can be spoofed. |
| Camera-style text metadata | Forged claims read back verbatim | Plain metadata is an unverified assertion. It is not authenticity proof. |

## Counterexamples

Each of these shows a signal failing in a specific, reproducible way:
- A **valid, trusted** signature on a **false** claim (P11).
- A validator that skips revocation accepts a revoked key as trusted (P13).
- One pixel value changed by 1 gives the same state as a crop or recompression (P03–P06). Hard bindings cannot tell benign from malicious changes.
- An ordinary OS image converter strips provenance and text metadata (P15, P16, M02, M03).
- Unsigned metadata can be edited while the manifest stays valid (P07).
- A watermark copied without the key passes detection (copy attack).
- A 1-pixel crop defeats a fixed-origin watermark detector.

## Coverage limits

- **Toy schemes.** Real C2PA, real watermarks and real detectors were not tested, so their behaviour may differ. Production watermarks may be more robust, and production C2PA validators implement more checks.
- **Synthetic procedural images**, not outputs of trained generative models and not camera photographs. Pixel statistics differ from social-media content.
- **Small and deterministic:** 12 images per family, 256×256, one machine and one run. The null calibration uses 960 trials, so it cannot resolve false-positive rates much below about 0.3%.
- **Processing.** Local tools (libjpeg-turbo, libwebp, macOS `sips`) stand in for platform processing. They are not a model of any platform's pipeline. Screenshots, screen re-capture, filters and video were not tested.
- **No shift or scale search** in the watermark detector. Adding one would recover cropped marks but raise the false-positive rate through multiple comparisons. This was not measured.
- **No base rates.** No measured prevalence was used, and no detector was evaluated.

## Actual C2PA evaluation (official c2patool; offline)

This part used one narrowly approved download: the official C2PA command-line tool, plus a few official test files. It is kept separate from the toy preparation. Full tables are in [`RESULTS_ACTUAL_C2PA.md`](RESULTS_ACTUAL_C2PA.md), and machine-readable results are in [`results/actual_c2pa/actual_c2pa_results.json`](results/actual_c2pa/actual_c2pa_results.json).

**Inputs.** These are not committed; obtain them from the sources below and check the hashes.
- **Tool.** `c2patool` v0.27.23, macOS universal build, from https://github.com/contentauth/c2pa-rs/releases/tag/c2patool-v0.27.23.
  - The asset `c2patool-v0.27.23-universal-apple-darwin.zip` is 20,800,495 bytes. Its SHA-256 is `380647e657ed16bb7e61982bd52f6c0b49a1cd92f09dbef49febd0f4c439a673`, matching GitHub's recorded digest.
  - The licence is MIT OR Apache-2.0.
  - The binary is ad-hoc signed only (no Developer ID or notarization). It was run from the experiment folder and never added to `PATH` or installed system-wide.
  - Extract it to `tools/c2patool-dl/extracted/`, or set `AUTHEXP_C2PATOOL_DIR`.
- **Official test files** (CC-BY-SA-4.0). Five files from https://github.com/c2pa-org/public-testfiles under `legacy/1.4/image/jpeg/`: `adobe-20220124-CA.jpg`, `-E-sig-CA.jpg`, `-E-dat-CA.jpg`, `-E-uri-CA.jpg` and `truepic-20230212-landscape.jpg`. Each matched GitHub's recorded git blob hash. Their content was inspected before use: ribbons and a landscape, with no people. Place them in `samples/official/`.
- **Bundled test credentials.** These are the `sample/` files in the release zip. The signing certificate's subject is "C2PA Test Signing Cert", with OU "FOR TESTING_ONLY", valid 2022-06-10 to 2030-08-26.

**Offline controls:**
- Every `c2patool` run is wrapped in `sandbox-exec` with all network access denied.
- [`actual_c2pa/settings/offline.toml`](actual_c2pa/settings/offline.toml) disables remote-manifest and OCSP fetching and allows no network hosts.
- Trust anchors come from local files only.
- No timestamp authority is used when signing. The bundled example manifest names one; it is not used.

**Run:** `python3 actual_c2pa/run_actual_c2pa.py`

**Results of the recorded run:**

| Input | No trust anchors | C2PA test trust anchors | What this supports |
|---|---|---|---|
| Official `CA` sample (documented valid) | `Valid`, with `signingCredential.untrusted` | `Trusted` | Intact and validly signed; "trusted" only relative to the configured test root |
| Official `E-sig-CA` / `E-dat-CA` / `E-uri-CA` | `Invalid`: `claimSignature.mismatch` / `assertion.dataHash.mismatch` / `assertion.hashedURI.mismatch` | `Invalid` | Each documented failure is reproduced. `E-dat` decodes to pixels identical to `CA`: the binding covers file bytes, not appearance. |
| Official Truepic camera sample (production signer) | `Valid`, untrusted | `Valid`, untrusted | No production trust list was configured, because fetching one was out of scope. Untrusted here is not evidence of manipulation. |
| Bundled `image.jpg` | `NO_MANIFEST` | `NO_MANIFEST` | Absence is not evidence either way |
| Synthetic PNG or JPEG signed with test credentials, unchanged | `Valid`, untrusted | `Trusted` | The signer's declaration (`algorithmicMedia`) is intact |
| Same PNG: lossless re-compression (identical pixels), one value changed, 8 px crop, or manifest moved to another image | `Invalid` (`assertion.dataHash.mismatch`) | `Invalid` | Benign and malicious changes look the same, so no conclusion about origin |
| Same JPEG: lossless `jpegtran -copy all -optimize` | `Invalid` (`assertion.dataHash.mismatch`) | `Invalid` | Even a lossless transcode breaks the hard binding |
| Manifest chunk removed; macOS `sips` PNG or JPEG re-save; JPEG q75 re-encode; `jpegtran -copy none` | `NO_MANIFEST` | `NO_MANIFEST` | Ordinary conversions strip credentials |
| Synthetic image signed with test credentials but deliberately declared `digitalCapture` | `Valid`, untrusted | `Trusted` | **A valid, trusted signature on a false claim.** Trust attests the signer, not the truth. |

**Limits of the actual run:**
- One `c2patool` version on one machine.
- JPEG and PNG only; no video, audio or other formats.
- Only the C2PA *test* trust anchors were used. No production trust list, OCSP or revocation status was fetched.
- The synthetic signatures carry no trusted timestamp.
- `sips` behaviour is specific to this macOS version.
- Social-media platform pipelines were not tested, because that would have required uploads.

## Other actual signals (not evaluated)

See [`docs/ACTUAL_SIGNAL_ROUTES.md`](docs/ACTUAL_SIGNAL_ROUTES.md). In short:
- Production watermarks (`invisible-watermark`, TrustMark, Video Seal), SynthID and AI-image detectors were **not approved or run**, so they remain unevaluated.
- SynthID can only be checked by uploading to Google.
- AI-image detectors need PyTorch, model weights and a licensed test set.

## Relation to the research report

`docs/` contains the user-facing research report and its source ledger. The experiment illustrates these claims from the report, using toy stand-ins:
- a valid provenance signal supports specific claims, not truth;
- valid is not trusted;
- absence of provenance is not evidence either way;
- benign processing breaks hard bindings;
- watermarks can be removed or spoofed;
- plain metadata is unverified.

It does not test the report's claims about real-world detector performance, legal processes or NCII.
